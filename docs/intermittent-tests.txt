# RESOLVED, 2026-08-16: PreferenceTest#testListPreference — the scroll/click race, FIXED at source.
#
# This replaces an "UNRESOLVED / cannot explain" section written here earlier. That section was
# wrong in its conclusion and, more usefully, wrong in three specific readings that are worth
# preserving because each one looked like evidence.
#
# THE MECHANISM. The test did:
#
#     mActivity.runOnUiThread(() -> mActivity.scrollToPreference("list"));
#     onView(withText(R.string.title_list_preference)).perform(click());
#
# Two operations with nothing between them. A RecyclerView scroll is an animation across frames,
# not a backlog of looper messages, so Espresso considers the main thread idle while the target row
# is still moving. The click lands on nothing, the dialog never opens, and the failure surfaces
# several assertions later as a missing radio widget — which reads like a RENDERING fault at a
# point in the test far from the actual mistake.
#
# THE FIX. One atomic, synchronised action:
#
#     onView(withId(R.id.recycler_view)).perform(
#             CarUiRecyclerViewActions.actionOnItem(
#                     hasDescendant(withText(R.string.title_list_preference)), click()));
#
# `hasDescendant` is required: the ViewHolder matcher tests the ITEM VIEW, while `withText` matches
# the TextView inside it, so passing withText directly finds no item and the scroll fails with a
# PerformException. No new dependency — espresso-contrib already resolves, and
# CarUiRecyclerViewActions is this repository's own helper.
#
# WHAT DID NOT WORK, recorded so it is not retried:
#   - An IdlingResource sampling RecyclerView state. The scroll has not STARTED when Espresso next
#     polls, so every condition is already true and it reports idle immediately: a no-op wearing the
#     costume of a fix. Arming it explicitly before the scroll only moves the same problem to the
#     next frame.
#   - A fixed sleep before the click. It passes, and it is worse than nothing: it encodes frame
#     timing measured on one machine and returns on slower hardware as the same misleading symptom.
#
# THREE MISREADINGS THAT COST HOURS, all mine, all from the same failure dump:
#   1. "The dialog DID open — CarUiRecyclerView and the list title are in the hierarchy." They
#      belong to the PREFERENCE SCREEN, not the dialog. This produced a content-limiting theory.
#   2. "One radio widget rendered instead of three." Zero were rendered. The single occurrence was
#      the MATCHER'S OWN DESCRIPTION in the exception text. Counted wrong twice.
#   3. Treating a deterministic failure as environmental for six controls (cold boot, --fix,
#      -wipe-data, UXR state, driving state, isolation) because earlier truncations in the same
#      session HAD been environmental. The prior probability was real; the reasoning was not.
#
# The generalisable lesson, and the reason this is written at length: a symptom several assertions
# downstream of its cause will describe the wrong subsystem, confidently. When an Espresso failure
# says "view missing", check whether the step BEFORE it actually happened before theorising about
# why the view is absent.
#
# Also worth noting against the baseline-signature column: this failure and the recorded scroll/click
# race are BOTH NoMatchingViewException, so a type-level signature would not have separated them.
# That column is coarser than its introduction implied.

# RESOLVED, 2026-08-17: FocusAreaTest#testBoundsOffsetWithRtl - the accessibility-walk race,
# FIXED at source. No allowlist entry was ever added for it, and none is needed.
#
# The failure: IndexOutOfBoundsException thrown from inside
# ViewGroup.onInitializeAccessibilityNodeInfoInternal, reached via
# FocusArea.onInitializeAccessibilityNodeInfo. Seen twice at unchanged rotary source - 2026-08-16,
# where it killed the instrumentation process and truncated the suite at 9 of 100, and 2026-08-17
# in the media3-conversion-layer gate, where the run completed with exactly 1 failure. Counting the
# retained gate logs put it at 1 run in 20.
#
# The cause, which the earlier notes did not have: the tests called
# createAccessibilityNodeInfo() from the INSTRUMENTATION thread. That platform method reads the
# child count and then indexes the child list, so a layout running concurrently on the UI thread
# can empty the list between those two steps - "Index 1 out of bounds for length 0" exactly.
# testBoundsOffsetWithRtl is the one that hit it because setLayoutDirection(RTL) requests a
# relayout first, and the test posted only once, which guarantees another pass of the message loop
# and not that layout has settled. The other three call sites in that file had the same hazard and
# differed only in having no relayout in flight to lose the race to.
#
# The fix: all four go through a nodeOn(View) helper that creates the node on the view's own
# thread, so the walk can no longer interleave with layout.
#
# Verified: car-rotary-lib connectedDebugAndroidTest rc=0, 100 tests, 0 failures, 0 errors, with
# all four patched tests present in the run.
#
# The honest limit on that verification, stated because the number invites over-reading: ONE green
# run does not demonstrate a 1-in-20 failure is gone - 19 of 20 runs were already green before the
# fix. The claim being made is structural rather than statistical. The interleave is removed
# because the walk now happens on the thread that owns the view tree, and a green run is
# consistent with that but is not evidence for it. If this test fails again, the fix is wrong and
# the diagnosis above is the first thing to doubt.
#
# Why this is a fix and not an allowlist entry: an entry would have downgraded a future failure of
# this test from FAIL to INDETERMINATE, on a module unrelated to the work that surfaced it. The
# evidence bar for writing one had been met - and the entry was still the worse option, because the
# race was explicable and small. Same conclusion the PreferenceTest section below reaches.

# RESOLVED, 2026-08-18: ToolbarSearchTest#test_registerSearchListeners_callsListeners[1] and [3]
# -- the IME action race, FIXED at source. BOTH allowlist entries removed above.
#
# The test typed "hello\n" and relied on the trailing newline becoming a search submission. That
# only happens if the IME translates the newline into an editor action, and in SearchMode.EDIT that
# translation races an IME restart: SearchView.setPlainText(true) switches imeOptions from
# IME_ACTION_SEARCH to IME_ACTION_DONE and then calls InputMethodManager.restartInput(), which is
# asynchronous. A newline arriving before the IME has restarted is delivered as a plain character
# rather than an action, so onEditorAction never fires and the completed listener never runs.
#
# The parameter indices are what make this more than a plausible story. The four parameters are
# [0]=(plugin off, SEARCH), [1]=(plugin off, EDIT), [2]=(plugin on, SEARCH), [3]=(plugin on, EDIT).
# The two observed to fail were [1] and [3] -- exactly the two EDIT cases, across both plugin
# settings. Only EDIT calls setPlainText on this path, and only setPlainText restarts the input.
#
# The fix: type and submit separately, with pressImeActionButton(), which performs the editor action
# directly on the current input connection instead of hoping the IME derives one. SearchView's
# handler accepts IME_ACTION_DONE *or* IME_ACTION_SEARCH, so it is correct on either side of the
# restart rather than only after it.
#
# Verified: ToolbarSearchTest, all 40 tests across all four parameters, 0 failures, rc=0.
#
# The same limit as the FocusArea fix applies and is worth repeating: one green run does not
# demonstrate that a roughly-2-in-8 intermittent is gone. The claim is structural, not statistical.
# What is stronger here than there is that the mechanism PREDICTS which parameters fail, and the
# prediction matches what was observed. If [0] or [2] ever fails, this diagnosis is wrong.
